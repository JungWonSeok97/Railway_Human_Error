# Railway_hep 코드 문제 지도 재검토

> 이 문서와 `results.json`은 입력 검증 강화 전의 검토 기록이다. 이후 `Railway_hep`에서 필수 문항 누락·잘못된 키·별칭 충돌을 거부하고 JSON 오류를 400/415로 반환하도록 수정했다. 최신 입력 계약은 [앱 README](../../Railway_hep/README.md)를 따른다. 아래 관측 결과와 당시 테스트 수는 이력을 보존하며, 현재 코드로 스크립트를 재실행하면 API 검사 결과가 달라진다.

검토일: 2026-11-18. 기준 문서: `Railway_hep 코드 문제 지도.pdf` 10쪽, 문서 표기일 2026-11-17.

현재 로컬 `Railway_hep` 소스와 실제 저장 모델을 기준으로 검토했다. 서비스 코드·모델·설문 원본은 수정하지 않았다. 이 디렉터리에는 검토 스크립트와 집계 결과만 추가했다.

**PDF의 5개 항목 중 보기 순서 오류는 해결됐고, HEP 계산과 이전 신경망 매핑 문제는 해당 구현이 제거되어 적용되지 않는다. 환경 모델의 단일 등급 출력은 해소됐지만 ‘나쁨’ 편향은 남아 있다. 일부 문항이 GMM 변환 과정에서 결과에 영향을 주지 못하는 현상도 남아 있다.**

## 검토 방법과 범위

- 기존 Python 테스트 20개와 JavaScript 테스트 16개를 다시 실행했다. 전부 통과했다.
- 현재 선택 코드의 데카르트 곱을 PSF별로 전부 열거했다. 총 89,262개이며, 이 중 PSF6이 82,944개이다. 모든 PSF를 서로 교차한 전체 작업자 프로필 수는 아니다.
- 실제 `build_catboost_features`와 저장 CatBoost 모델을 사용했다. 다른 문항을 고정하고 한 문항의 선택지만 바꿔 전처리 특성, 분류 확률, 최종 등급이 각각 달라지는지 검사했다.
- PSF4 전수 검사는 보조 CatBoost 경로를 대상으로 했다. 기본 `/api/predict`의 PSF4 공식 경로는 별도 API 요청으로 확인했다.
- PSF6의 원본 학습 데이터 2,950건을 다시 읽어 저장 모델로 재예측했다. 기존 메타데이터의 재예측 집계와 일치했고, 설문 및 모델 파일의 해시도 일치했다.
- GroupKFold 수치는 현재 모델 메타데이터의 기존 평가 기록을 검토한 것이다. 이번 검토에서 교차검증 모델을 다시 학습하지 않았다.
- 모델·원본 설문·노트북·매핑 XLSX·참고 PDF 등 보호 대상 21개 파일의 실행 전후 해시가 동일했다.

시나리오 전수 검사는 **현재 함수의 동작 검사**이다. 실제 발생 빈도나 미관측 상황에 대한 정확도 평가가 아니다. API는 Flask 테스트 클라이언트로, 화면은 실제 스크립트를 실행하는 자동 테스트로 확인했다. 실제 브라우저 시각 검증은 이번 범위에 포함하지 않았다.

## 1. 입력 보기 순서는 해결됨

현재 화면은 각 `<option>`의 `data-condition-code`에 명시된 코드를 보낸다. 화면 위치를 기준으로 번호를 다시 붙이지 않는다.

| 현재 응답 | 전송 코드 | 모델 입력 숫자 |
| --- | --- | ---: |
| 수면 8시간 이상 | `F.1.S.3.3` | 0 |
| 수면 6~8시간 | `F.1.S.3.2` | 1 |
| 수면 6시간 이내 | `F.1.S.3.1` | 2 |

근거: `Railway_hep/input.html:87`, `static/input-encoding.js:4`, `config/catboost_mappings.py:18`. 기존 코드 형식과 `.S.` 형식 별칭도 동일한 학습 값으로 해석된다. 다른 문항의 선택 코드를 보내면 거부한다.

환경 PSF는 온도·습도 양 끝 수준을 하나의 숫자로 합치지 않고 원래 범주로 전달한다. 실내 온도·습도의 낮음/중간/높음 구분도 별도 테스트를 통과했다.

따라서 PDF에 실린 옛 보기 순서 보정표를 현재 코드에 추가할 필요는 없다.

## 2. 환경: 항상 나쁨은 해소됐지만 편향은 남음

현재 사용 모델은 `models/환경_raw14_catboost.cbm`이며, 14개 원래 범주를 직접 받는다. 이전 `환경_catboost.cbm`과 환경 GMM은 기본 추론에서 사용하지 않는다.

| 검사 범위 | 전체 | 보통 | 나쁨 | 해석 |
| --- | ---: | ---: | ---: | --- |
| 이전 GMM 모델 + 현재 학습 인코딩에 맞춘 14개 선택 조합 | 82,944 | 0 (0%) | 82,944 (100%) | 동일한 원변수 영역에서 이전 모델 동작 확인 |
| 현재 원변수 모델 + 전체 선택 조합 | 82,944 | 1,784 (2.15%) | 81,160 (97.85%) | 현재 UI가 표현하는 입력 영역의 동작 |
| 안개·낙뢰를 학습에서 관측한 상태로 제한한 조합 | 20,736 | 446 (2.15%) | 20,290 (97.85%) | 범주는 관측됐어도 결합 시나리오는 미관측일 수 있음 |
| 저장 모델로 학습 데이터 재예측 | 2,950 | 64 (2.17%) | 2,886 (97.83%) | 학습 내 결과; 일반화 성능 아님 |
| 기존 원변수 시나리오 GroupKFold OOF 기록 | 2,950 | 132 (4.47%) | 2,818 (95.53%) | 같은 시나리오를 학습에서 제외한 평가 |

현재 학습 데이터의 실제 응답은 보통 805건(27.29%), 나쁨 2,145건(72.71%)이다. 기존 OOF 기록에서 실제 보통 805건 중 보통으로 맞힌 것은 54건으로, **보통 재현율 6.71%**이다. 균형 정확도는 51.54%, 일반 정확도는 71.90%이다. 모든 응답을 나쁨이라고 답하는 기준의 일반 정확도 72.71%보다도 낮다. 따라서 보통 출력이 생겼다는 사실만으로 분류 성능이 충분해졌다고 판단할 수 없다.

PDF의 17,776개 조합은 당시 검사 범위이다. 현재 14개 선택지의 이론적 조합 수는 `2^10 × 3^4 = 82,944`이며, 이번에는 이를 전부 검사했다. 이전 GMM 모델에 실제 전달되는 서로 다른 복합 입력은 이 원변수 영역에서 486개였다. 원변수 조합 수, 복합 입력 수, 설문 응답 건수는 서로 구분해야 한다.

**학습 데이터에서 안개와 낙뢰는 각각 ‘발생할 경우’ 한 범주만 관측된다.** 현재 모델에서도 두 변수의 중요도는 0이고, 두 답을 바꿔도 분류 확률까지 동일하다. 그 외 12개 원변수는 각각 확률과 등급에 영향을 주는 조합이 존재한다.

권고: PSF6 원변수 입력을 유지하면서 보통 재현율·균형 정확도·혼동행렬을 성능 판단 기준에 포함한다. 보통 사례와 현재 관측되지 않은 안개·낙뢰 범주를 보강하고, 모델 설정·가중치·임계값을 비교할 경우 학습 데이터와 분리한 평가로 검증해야 한다. 임계값을 낮춰 보통 비율만 늘리는 것을 정확도 개선으로 간주하면 안 된다.

## 3. GMM에서 일부 하위 문항 변화가 사라짐

단순히 평균 판정 수준이 같다는 사실만으로 문항이 쓰이지 않는다고 판단하지 않았다. 다른 모든 문항 조합을 고정한 상태에서 해당 문항을 바꾸어 확률과 전처리 특성까지 검사했다.

### PDF에 나온 다섯 문항의 현재 상태

| 문항 | 코드 | 다른 문항 고정 조합 수 | 등급이 달라지는 조합 수 | 분류 확률 변화 | 현재 판정 |
| --- | --- | ---: | ---: | --- | --- |
| 장비 가용성 | F.2.S.1 | 729 | 222 | 있음 | PDF의 무영향 현상은 현재 재현되지 않음 |
| 컴퓨터 지원 시스템의 적절성 | F.2.S.3 | 486 | 0 | 없음 | GMM 출력부터 동일 |
| 절차의 유무·가용성 | F.3.S.1 | 243 | 93 | 있음 | PDF의 무영향 현상은 현재 재현되지 않음 |
| 의사결정 대안의 수 | F.8.S.2 | 324 | 0 | 없음 | GMM 출력부터 동일 |
| 추론해야 하는 정보의 양 | F.8.S.6 | 324 | 0 | 없음 | GMM 출력부터 동일 |

장비 가용성과 절차의 유무는 현재 학습 인코딩이 0/1이다. PDF의 0/2 검사 결과를 현재 구현에 그대로 적용할 수 없다.

예를 들어 PSF2 `System_Support`는 컴퓨터 지원 시스템(F.2.S.3)과 타 기기 연계성(F.2.S.6)을 묶는다. 저장된 GMM의 현재 출력은 다음과 같다.

| 컴퓨터 지원 시스템 입력 ↓ / 타 기기 연계성 입력 → | 0 | 1 | 2 |
| --- | ---: | ---: | ---: |
| 0 | 0 | 1 | 2 |
| 1 | 0 | 1 | 2 |
| 2 | 0 | 1 | 2 |

타 기기 연계성을 1로 고정하면 컴퓨터 지원 시스템을 0·1·2로 바꿔도 최종 복합 특성은 모두 1이다. CatBoost에 들어가는 입력이 같으므로 분류 확률도 바뀔 수 없다.

PSF8의 `Decision_Complexity`도 F.8.S.2 변화가 사라지고 F.8.S.3에만 따라 변한다. `Information_Complexity`는 F.8.S.6 변화가 사라지고 F.8.S.5에만 따라 변한다.

근거: `config/catboost_config.py:35,176,187`, `preprocessing/catboost_features.py:271`, 저장된 GMM 번들. 정확한 3×3 변환표는 `results.json`의 `gmm_mapping_tables`에 있다.

이것은 해당 문항이 현실에서 중요하지 않다는 증거가 아니다. 현재 저장된 군집 변환이 그 문항의 변화를 전달하지 않는다는 뜻이다. 문항을 삭제하기 전에 군집 묶음·군집 수·변환 방식을 재검토하거나 해당 원변수를 함께 사용하는 대안을 동일한 평가 분할에서 비교하는 편이 적절하다. PSF2·4·8의 GMM 전체를 즉시 폐기해야 한다는 결론은 아니다.

## 4. PSF4는 기본 API와 보조 API를 구분해야 함

`app.py:110`에서 기본 `/api/predict`의 F.4는 `predict_psf4_formula()`로 분기한다. 이 함수는 `training_elapsed_months`만 사용한다. 화면은 교육·훈련 7문항도 함께 보내지만 현재 기본 배수에는 반영되지 않는다.

교육 후 12개월로 고정하고 7개 응답을 전부 첫 번째 보기에서 마지막 보기로 바꾸어도 결과는 모두 **보통, 1.000배**였다. 근거: `input.html:946`, `predictors/psf4_formula.py:68`, `results.json`의 `education_same_months`.

반면 `/api/predict/4`와 CatBoost 일괄 별칭은 F.4의 GMM·CatBoost 모델을 사용한다. 이 보조 경로에서도 다음 두 문항은 GMM 출력에 영향을 주지 않았다.

| 문항 | 코드 | 영향을 잃는 복합 특성 |
| --- | --- | --- |
| 직무능력 평가 빈도 | F.4.S.4 | Training_Frequency |
| 장비 사용 지식의 숙련도 | F.4.S.7 | Technical_Knowledge |

‘PSF4는 GMM을 유지한다’는 설명은 **보조 모델 경로에 대해서는 맞지만 기본 웹앱 경로에 대해서는 충분하지 않다.** 기본 화면에서도 7개 응답을 반영할지, 경과 개월 수 공식을 유지할지 지표 정의를 명확히 해야 한다. 공식을 유지한다면 화면에서 해당 7문항이 현재 배수에 미반영된다는 사실을 알 수 있게 하는 것이 좋다.

## 5. PDF 외에 확인된 API 입력 검증 문제

### 누락 문항·잘못된 키를 숫자 1로 대체함

PSF6 이외의 CatBoost 입력은 `config/mappings.py:38` 및 `preprocessing/catboost_features.py:365`에서 누락된 값을 1로 채운다. 잘못 쓴 키는 읽지 않고, 구형 키와 신규 키의 값이 충돌해도 신규 키를 우선한다.

실제로 다음 요청은 HTTP 200을 반환한다.

```http
POST /api/predict/1
Content-Type: application/json

{}
```

응답은 나쁨, 배수 14.45이며 보통 33.22%·나쁨 51.40%·매우나쁨 15.38%이다. 작업부하 다섯 문항을 하나도 받지 않았지만 모두 숫자 1을 입력해 판단한 결과다.

기본 `/api/predict`에 F.1의 근무시간 하나만 보내도 나머지 문항을 1로 채워 예측한다. 따라서 검증용 API에만 해당하는 현상이 아니다. PSF6은 같은 종류의 누락을 400으로 거부한다.

권고: 제공된 PSF 내부에서 필수 문항 누락·알 수 없는 키·별칭 충돌을 명시적으로 거부한다. 일부 PSF만 요청하는 기존 계약과, 한 PSF의 문항이 빠진 요청은 구분한다. 전자는 현재처럼 전체 곱을 null로 반환할 수 있지만, 후자를 정상 시나리오로 추정하지 않는 편이 안전하다.

### 잘못된 JSON을 서버 오류 500으로 응답함

`/api/predict`에 `{bad`를 JSON으로 보내면 본문에는 `400 Bad Request`가 들어 있지만 HTTP 상태는 500이다. `request.json`의 HTTP 예외를 일반 `Exception` 처리에서 500으로 바꾸기 때문이다. 근거: `app.py:88,135`.

입력 오류를 400/415로 유지하고, 실제 내부 오류만 500으로 반환하도록 예외 처리를 구분할 필요가 있다.

## 6. 표시·문서·재현성의 추가 확인 사항

- 현재 요약·상세·시간별·월별 화면은 배수의 곱을 표시한다. 분류 확률의 % 표시는 별개이다. M=54→55와 교육 후 44→45개월의 배수가 정상적으로 증가하는 테스트가 통과했다.
- 환경 비의 두 번째 보기에는 여전히 `10mm/s`, 눈 `1cm/s`가 표시된다(`input.html:478`). 첫 번째 보기는 시간당 단위다. 원본 설문 문구를 모델 범주 토큰으로 유지한 결과이며, UI 단위는 원설계 의도를 확인한 뒤 고쳐야 한다. 표시만 수정하고 안정된 선택 코드를 유지할 수 있으므로, 화면 문구 교정 때문에 학습 토큰까지 즉시 바꿀 필요는 없다.
- 저장된 GMM의 scikit-learn 버전은 1.9.0, 이번 실행 환경은 1.7.2라서 불일치 경고가 발생한다. 이번 검사는 통과했지만 저장·실행 버전을 고정한 재현 환경이 필요하다. `requirements.txt`에는 버전 고정이 없다.
- 최종 확인 시 상위 저장소의 `README.md`·프로젝트 지도와 `Railway_hep/README.md` 모두 PSF 배수 제공 구조로 갱신되어 있었다. 과거 참고 PDF의 HEP 계산 설명과 현재 API 계약은 구분해야 한다.

## 후속 작업 우선순위

1. 누락·오타·충돌 입력을 정상 예측으로 처리하는 API 검증부터 보완한다. 이는 모델 재학습 없이 수정 가능한 동작이다.
2. PSF4 기본 배수의 정의를 공식 기반/설문 모델 기반 중 명확히 하고 화면 및 문서와 맞춘다.
3. PSF2·8 및 보조 PSF4의 GMM에서 정보가 사라지는 문항에 대해 입력 표현을 비교한다. 모델을 바꾸면 동일 평가 분할로 검증한다.
4. PSF6은 보통 재현율과 데이터 범주 부족을 중심으로 개선한다. 보통 출력 비율만을 목표로 삼지 않는다.
5. 오류 HTTP 상태, 표시 단위 및 패키지 버전을 정리한다.
