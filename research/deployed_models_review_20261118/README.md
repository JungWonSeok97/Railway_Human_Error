# 저장 CatBoost 모델과 실제 추론 경로 재검토

> 이 문서와 `results.json`은 입력 검증 강화 전의 검토 기록이다. 이후 `Railway_hep`에서 4절의 필수 문항 누락·잘못된 키·별칭 충돌 및 JSON 오류 상태 처리를 수정했다. 최신 입력 계약은 [앱 README](../../Railway_hep/README.md)를 따른다. 당시 관측 결과와 소스 해시는 보존하며, 현재 코드로 스크립트를 재실행하면 API 검사 결과와 소스 해시가 달라진다. 모델 파일은 이번 입력 검증 수정 대상에 포함되지 않는다.

검토일: 2026-11-18. 대상은 `Railway_hep/models/*.cbm` 및 현재 API의 입력 변환·모델 선택·출력 처리다.

## 판단 기준 정정

`CatBoost_Result`는 사용자가 여러 조건을 시험한 탐색 노트북이다. 노트북의 함수 재정의, 부분 실행, 출력 혼재를 그 자체로 운영 모델의 결함이라고 판단하지 않는다. 앞선 검토의 해당 사항은 실험 기록의 해석에 한정하며, 저장 `.cbm`의 유효성과 구분한다.

현재 요청 처리 경로는 노트북을 실행하지 않고 저장 모델과 저장 GMM을 읽는다. 학습 시의 노트북 상태가 매 요청마다 모델을 바꾸는 구조가 아니다. 별도 재학습 CLI는 검토된 전처리 노트북 일부를 해시로 고정해 재사용하지만, 이는 운영 추론과 별개다.

**이번 확인에서 모델 파일 손상, 설정과 다른 특성 순서, 출력 등급 뒤바뀜은 발견되지 않았다. 다만 입력 누락을 정상 예측하는 API 처리, PSF6의 강한 나쁨 편향, 보조 PSF4 모델의 좋음 미출력, 일부 GMM 문항 정보 손실은 실제 운영 아티팩트에서도 재현된다.**

추가 파일 `환경_catboost.cbm`은 이전 6개 GMM 특성 모델이다. 현재 설정에 연결되지 않으며, 기본 API가 구형 환경 모델을 잘못 선택하는 현상은 없었다.

빈 캐시에서 실제 Flask 요청을 보내 로드된 모델을 추적했다.

- `/api/predict`: CatBoost PSF **1·2·3·5·6·7·8**, GMM **2·8**을 로드했다. PSF4는 개월 수 공식이다.
- `/api/catboost/predict`: CatBoost PSF **1~8**, GMM **2·4·8**을 로드했다.
- `/api/predict/4`: 교육·훈련 CatBoost 경로다.

따라서 ‘PSF2·4·8에 GMM을 사용한다’는 설명은 CatBoost 경로에서는 맞지만, 기본 일괄 API의 PSF4에는 해당하지 않는다. 이것이 의도된 제품 요구사항인지 확인해야 할 경로 차이이며, 현재 코드가 노트북 결과를 섞어 읽는 문제는 아니다. 검토 중 경로를 변경하지 않았다.

근거: `app.py:110`, `app.py:225`, `app.py:292`, `config/catboost_config.py`, `preprocessing/catboost_features.py:21`.

## 2. 정상 확인 사항

- `.cbm` **9개 모두** 실제 CatBoost로 로드했다. 모두 트리 500개를 가진 모델이다.
- 설정에서 사용되는 8개 모델은 저장 특성 이름·순서, 전체 특성의 범주형 지정, 출력 클래스 집합이 API 설정과 일치했다. 응답자 ID 등 식별자는 모델 입력 특성에 없었다.
- PSF6은 특성 이름뿐 아니라 내장 입력 스키마와 스키마 해시도 로더에서 검증한다. 원래 14개 범주와 구형 숫자 인코딩을 구분한다.
- 가능한 출력 등급별 대표 사례 **21개**에서 `.cbm` 직접 확률, API의 코드별 확률, 선택 등급, PSF 배수가 일치했다. 확률은 유한하며 합이 1이었다.
- 기본 및 CatBoost 일괄 API에서 8개 결과와 배수 곱을 검증했다. 진단·수행·최종 HEP를 다시 계산하지 않는다.
- 기존 Python **20개**, JavaScript **16개** 테스트를 현재 파일로 다시 실행해 모두 통과했다. 이 테스트 통과가 아래 입력 검증 결함까지 없다는 뜻은 아니다.
- 앞선 재학습 검증에 사용한 원본·모델 해시가 현재도 모두 일치했다. 이전 검증에서 기존 8개 모델의 23,462개 학습 행 확률은 재학습 모델과 같았다. **이번에는 재학습하지 않았으며, 그 검증의 환경 모델은 구형 GMM 모델이다.**
- 현재 환경 원변수 모델은 모델·설문 해시와 재구성 데이터 지문이 메타데이터와 일치했고, 학습 데이터 2,950건의 재예측 집계도 기록과 정확히 일치했다.

수면시간은 현재 선택 코드가 학습 인코딩과 연결된다. 8시간 이상→0, 6~8시간→1, 6시간 이내→2다. 노트북의 탐색 실행 순서만을 이유로 기존 모델을 일괄 재학습할 근거는 없다.

## 3. 저장 모델의 전체 선택 조합 예측

실제 `build_catboost_features`와 저장 `.cbm`을 사용해 현재 정의된 선택 코드의 데카르트 곱을 PSF별로 모두 예측했다. 총 **89,262개**다. PSF4는 CatBoost 경로이며 기본 공식의 출력 분포가 아니다.

| PSF | 조합 수 | 저장 모델의 예측 건수 |
| --- | ---: | --- |
| PSF1 작업부하 | 243 | 나쁨 96 / 매우나쁨 10 / 보통 137 |
| PSF2 장비 및 기기 | 1,458 | 나쁨 192 / 보통 1,182 / 좋음 84 |
| PSF3 절차 및 지침 | 486 | 나쁨 138 / 보통 271 / 좋음 77 |
| PSF4 교육 및 훈련 | 2,187 | 나쁨 216 / 보통 1,971 |
| PSF5 의사소통 | 729 | 나쁨 233 / 보통 496 |
| PSF6 환경 | 82,944 | 나쁨 81,160 / 보통 1,784 |
| PSF7 작업절차 | 243 | 나쁨 152 / 보통 81 / 좋음 10 |
| PSF8 복잡성 | 972 | 매우 높음 117 / 보통 90 / 약간 높음 765 |

이 표는 모든 선택 조합을 동일한 비중으로 세는 **모델 동작 검사**다. 실제 상황의 발생 빈도, 설문 응답 비율, 예측 정확도가 아니다. 물리적으로 함께 발생하기 드문 조합과 학습에서 보지 못한 조합도 포함된다.

### PSF6: 보통이 나오지만 나쁨 편향이 큼

현재 모델은 보통 **1,784/82,944 = 2.15%**, 나쁨 **81,160/82,944 = 97.85%**를 출력한다. 이전 GMM 모델은 같은 원변수 영역에서 모두 나쁨이었다. 구형 모델을 잘못 읽는 문제가 아니라 현재 원변수 모델 자체에서도 나타나는 분포다.

현재 파일과 연결된 기존 GroupKFold 평가 기록은 다음과 같다. 이번 검토에서 fold 모델을 다시 학습한 것은 아니다.

| 평가 항목 | 값 |
| --- | ---: |
| 실제 보통 / 나쁨 응답 수 | 805 / 2,145 |
| OOF 보통 / 나쁨 예측 수 | 132 / 2,818 |
| 일반 정확도 | 71.90% |
| 항상 나쁨을 출력하는 기준 정확도 | 72.71% |
| 보통 재현율 | 54/805 = 6.71% |
| 균형 정확도 | 51.54% |

원변수 모델로 바뀌어 단일 출력 문제는 해소됐지만, 보통을 충분히 구분한다고 판단하기 어렵다. 숫자 코드를 뒤집거나 확률 표시를 고치는 것으로 해결할 현상은 아니다. 설정·가중치·임계값·입력 정보를 비교하되, 보통 출력 비율만 인위적으로 늘리지 말고 분리한 평가에서 재현율과 오탐을 함께 확인해야 한다.

또한 안개·낙뢰는 학습에서 각각 발생하는 범주만 관측된다. 두 문항을 바꿔도 저장 모델의 확률까지 동일했다. 이는 코드가 변수를 누락해서가 아니라 현재 데이터와 학습 모델이 두 범주 차이를 학습하지 못한 한계다.

### 보조 PSF4: 좋음이 최종 선택되지 않음

`교육_및_훈련_catboost.cbm`에는 **좋음·보통·나쁨 세 클래스가 모두 존재**한다. 그러나 유효 원변수 2,187개 조합, 변환 후 243개 고유 모델 입력에서 최종 선택은 보통 1,971건·나쁨 216건이며 좋음은 0건이다.

좋음 확률이 가장 높은 사례조차 좋음 **46.93%**, 보통 **47.82%**, 나쁨 **5.24%**다. API가 좋음을 다른 코드로 바꾼 것이 아니라, 모델의 최대 확률 등급이 보통이다. 좋음의 확률 자체가 항상 0인 것도 아니다.

이는 운영의 세 등급 구분이 충분한지 평가해야 할 사항이다. 한 fold 모델의 OOF 출력에 좋음이 있었다고 해서 전체 데이터로 저장한 최종 모델에서도 반드시 좋음이 선택되는 것은 아니다. 최종 전체 학습 모델과 fold별 모델은 서로 다른 모델이다.

기본 `/api/predict`는 PSF4 공식이므로 이 현상을 기본 화면의 교육·훈련 배수로 일반화하면 안 된다.

## 4. 실제 입력 처리 결함

### 중요: PSF 내부 필수 문항 누락을 숫자 1로 채움

PSF6 이외의 CatBoost 입력은 `preprocessing/catboost_features.py:365`와 `config/mappings.py:38`에서 누락값을 1로 대체한다.

`POST /api/predict/1`에 `{}`를 보내면 HTTP **200**, 나쁨, **14.45배**를 반환한다. 응답 문항이 하나도 없는데도 다섯 문항을 모두 1로 만든 예측이다. `/api/predict`에 근무시간 한 문항만 넣어도 나머지 문항을 채워 성공한다. 키 오타와 별칭 간 값 충돌도 현재는 명시적으로 거부하지 않는다. PSF6의 문항 누락은 400으로 거부하므로 검증 규칙이 PSF마다 다르다.

일부 PSF만 요청하는 기능과, 제공한 PSF 내부의 문항이 빠진 것은 구분해야 한다. 전자는 허용하되 후자는 명시적인 검증 오류로 처리하는 것이 적절하다. 이 수정에는 모델 재학습이 필요하지 않다.

### 입력 JSON 오류를 500으로 변환

`POST /api/predict`에 잘못된 JSON `{bad`를 전송하면 400 예외가 일반 예외 처리에 잡혀 HTTP **500**이 된다. 입력 오류 상태와 실제 서버 오류를 구분할 필요가 있다. 근거: `app.py:88`, `app.py:135`.

## 5. 저장 GMM에서 일부 문항 정보가 사라짐

모든 다른 문항 조합을 고정하고 해당 문항만 바꾸어 전처리 출력과 모델 확률을 비교했다.

| 모델 | 확률까지 전혀 바뀌지 않는 문항 | 범위 |
| --- | --- | --- |
| PSF2 | 컴퓨터 지원 시스템의 적절성, F.2.S.3 | 기본·CatBoost 경로 |
| PSF8 | 의사결정 대안의 수, F.8.S.2 | 기본·CatBoost 경로 |
| PSF8 | 추론해야 하는 정보의 양, F.8.S.6 | 기본·CatBoost 경로 |
| PSF4 | 직무능력 평가 빈도, F.4.S.4 | 보조 CatBoost 경로 |
| PSF4 | 장비 사용 지식의 숙련도, F.4.S.7 | 보조 CatBoost 경로 |

예를 들어 PSF2에서 타 기기 연계성을 1로 고정하면 컴퓨터 지원 시스템을 0·1·2로 바꿔도 GMM의 `System_Support`는 모두 1이다. CatBoost는 같은 입력을 받으므로 같은 확률을 반환한다.

이는 노트북 실행 상태와 관계없이 **현재 저장 GMM과 CatBoost 조합의 성질**이다. 문항의 실제 중요성이 없다는 증거는 아니다. GMM을 유지하더라도 군집 설정 또는 일부 원변수를 함께 쓰는 대안을 동일한 평가 조건으로 비교할 수 있다. 입력 표현을 바꾸면 해당 PSF 모델의 재학습이 필요하다.

## 6. 배포 환경과 판단 범위

저장 GMM은 scikit-learn 1.9.0 정보가 있고 현재 실행은 1.7.2라 불일치 경고가 발생한다. 이번 로드·예측·테스트는 통과했지만 `requirements.txt`에 버전 고정이 없어 재현 가능한 배포 환경을 마련해야 한다. 경고가 실제 오예측의 원인이라고 단정하지 않는다.

`.cbm`이 정상 로드되고 API와 연결된다는 사실과, 현장 데이터에서 충분한 예측 성능을 보인다는 사실은 별개다. 이번에는 새 외부 평가자료를 확보하거나 모델을 재학습하지 않았다. 성능 판단에 노트북 후반의 튜닝 최고 점수를 임의로 연결하지 않았다.

## 7. 수정 우선순위

1. 모델 재학습 없이 가능한 PSF 입력 필수값·키·별칭 충돌 검증 및 JSON 오류 상태 처리.
2. PSF6의 보통 구분과 보조 PSF4의 좋음 구분 성능을 배포 대상에 맞게 평가·개선.
3. PSF2·8 및 보조 PSF4의 GMM 정보 손실을 비교 실험으로 평가. GMM 전체 폐기를 전제하지 않음.
4. 기본 API와 개별 API의 PSF4 정의를 제품 요구사항과 맞추고 문서화.
5. 모델·전처리·입력 스키마·패키지 버전을 묶어 관리.

이번에는 원본 노트북·모델·설문·운영 코드 **53개 파일의 해시가 실행 전후 동일**했다. 검토 스크립트와 집계 자료만 이 폴더에 추가했다.

## 재현 자료

- `review_models.py`: 저장 모델 전수 조합 검사, API 모델 연결 검사, 메타데이터 및 보호 파일 검증. 모델을 학습·교체하지 않는다.
- `results.json`: 모델 목록·해시, 조합 예측 집계, 문항 민감도, 대표 API 비교, 실제 로드 경로 및 재현 요청.
- 실행: 저장소 루트에서 `python -B research/deployed_models_review_20261118/review_models.py`.
- 회귀 테스트: `Railway_hep`에서 `python -B -m unittest discover -s tests -p 'test_*.py'` 및 `node --test tests/forecast.test.cjs tests/input-encoding.test.cjs tests/psf-multipliers.test.cjs`.

응답자 식별 정보나 개인별 설문 행은 산출물에 포함하지 않았다.
