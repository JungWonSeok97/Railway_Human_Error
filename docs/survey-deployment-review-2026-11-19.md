## 추가 재현 검토

같은 날 저장 API·기본 설문 완료 처리·관리자 집계의 실제 소스를 분리 실행했다. TypeScript의 타입 표기만 제거하고 DB·HTTP·DOM을 모의 처리했다. 운영 서비스에는 요청을 보내지 않았다.

| 재현 조건 | 확인한 결과 | 해석 |
| --- | --- | --- |
| API에 빈 객체 전달 | DB insert 호출까지 진행 | API 자체에 필수 필드 검증이 없음 |
| `round: 99`, `questions: []`, 잘못된 근속년수 | insert 호출, 근속년수 0으로 변환 | 회차·문항·근속년수 검증 필요 |
| 미등록 PSF 999, 미등록 답변, 근속년수 -5 | insert 호출, -5 유지 | 선택지 허용 목록과 수치 범위 검증 필요 |
| 기본 설문에서 응답 대기 중 완료 처리 2회 실행 | 같은 1회차 POST 2건, 두 처리 모두 다음 회차를 2로 변경 | 전송 중 잠금 및 서버 중복 방지 필요 |
| 1~30회 응답에 1회차 중복 레코드 추가 | 완료 회차 `31 / 30`, 평균 완료율 `103%` | 레코드 개수 대신 세션별 고유 완료 회차를 집계해야 함 |

모의 DB는 입력을 허용하도록 구성했으므로, API가 insert를 시도한다는 사실과 운영 DB가 실제 저장을 허용한다는 것은 구분한다. 관리자 집계는 주어진 31개 레코드를 대상으로 코드 계산 결과를 재현했다. 진행률을 100%로 잘라 표시하는 것만으로 중복 데이터 문제를 해결할 수는 없다.

검사 코드: `rail-psf-accuracy-memo/build/survey-review-20261119/reproduce.cjs`. `survey/node_modules`가 없어 정식 Next.js build/lint는 수행하지 않았다. survey 서비스의 실행 코드는 변경하지 않았다.

## 설문 구성

Next.js/React가 설문을 표시하고, 회차별 응답을 `/api/survey`가 Supabase `survey_responses`에 저장한다. 모델 학습과 PSF 예측은 이 앱의 기능이 아니다.

- 기본 `/survey`: 8개 PSF 중 2개를 선택하고 같은 두 PSF에 대해 조건을 바꾸며 30회 응답한다.
- 그룹 설문: group1은 PSF1·2, group2는 PSF3·4, group3은 PSF5·6, group4는 PSF7·8이다.
- 한 번 완료하면 30개 회차 레코드에 총 60개 PSF 판단 응답이 저장되는 구조다.
- 회차마다 조건 조합을 무작위로 뽑는다. 참여자 사이 또는 한 참여자 안에서 중복이 생길 수 있다.
- 조건과 전문가 답변은 문구 문자열로 저장한다. 이 단계에서 GMM 군집이나 0/1/2 모델 인코딩을 수행하지 않는다.

## 주요 발견

### 1. 환경 설문에 정상 기상 조건이 부족하다

위치: `survey/src/lib/surveyData.ts:68–82`, 배포된 기본·그룹 설문 JavaScript.

- 낙뢰: `낙뢰가 발생할 경우` 하나뿐이다.
- 안개: `안개가 발생할 경우` 하나뿐이다.
- 황사: 사물 식별이 어려운 경우와 숨쉬기가 불편한 경우만 있다.

따라서 다른 조건이 양호해도 낙뢰·안개가 항상 포함되며 황사도 불편한 상황으로 제시된다. 이 설계가 환경 응답을 나쁨 쪽으로 유도할 가능성이 있다. 이는 코드에서 확인한 설계와 그에 대한 해석이며, 이것만으로 기존 모델의 나쁨 100% 출력 원인이나 영향 크기가 입증된 것은 아니다.

환경 조합은 2수준 변수 8개, 3수준 변수 4개, 고정 변수 2개로 `2^8 × 3^4 × 1^2 = 20,736`개다. 예측 앱의 선택지 전체 조합 수와 구분해야 한다.

권장: 정상·악조건의 조사 범위 및 배정 비중을 재검토한다. 새 범주를 추가하면 설문 버전, 응답 변환 규칙, 학습 스키마를 함께 관리하고 기존 응답은 원문대로 보존한다.

### 2. 관리자 로그인에 서버 인증이 없다

위치: `survey/app/admin/page.tsx:14–22`, `survey/app/admin/dashboard/page.tsx:34–68`, `survey/src/lib/supabase.ts`.

관리자 비밀번호를 클라이언트에서 비교하고 `sessionStorage` 플래그로 화면 진입을 판단한다. 대시보드는 브라우저의 공개 키로 DB를 직접 조회한다. 이 플래그는 서버 권한 검증이 아니며 비밀번호를 클라이언트 환경 변수로 옮기는 것만으로 해결되지 않는다.

실제 개인정보 조회 가능 여부는 DB RLS 정책에 달려 있다. 이번에는 운영 데이터 접근을 시도하지 않았으므로 공개 유출이 확인됐다고 단정하지 않는다.

권장: 실제 로그인 세션과 관리자 권한을 서버/DB에서 검증하고 익명 사용자의 응답 전체 조회를 제한한다.

### 3. 저장 API의 데이터 검증·중복 방지가 부족하다

위치: `survey/app/api/survey/route.ts:35–75`.

요청 JSON을 받아 바로 insert한다. 코드에는 회차 1~30 범위, PSF ID·선택지·조건의 허용 목록, 두 문항 배정의 일치, 문자열 길이, 중복 요청 식별자 검사가 없다. 근속년수가 잘못된 문자열이면 0으로 바뀐다.

그룹 폼에는 요청 중 버튼을 막는 로직이 있지만 기본 `/survey` 폼에는 없다. 서버에서도 동일 회차의 재요청을 식별하지 않는다. DB 자체의 별도 제약조건 유무는 확인하지 못했다.

대시보드는 이름+사번으로 묶은 레코드 수를 완료 회차로 세기 때문에, 재시작·재전송·다른 그룹 응답이 섞이면 진행률이 부정확해질 수 있다.

권장: `survey_session_id`와 회차를 기준으로 유일성을 보장하고 서버에서 설문 버전·문항·조건·응답을 검증한다. 기본 폼에도 전송 중 중복 클릭 방지를 적용한다.

### 4. 새로고침 후 이어하기가 없다

위치: `survey/src/components/SurveyForm.tsx:12–43`, `survey/app/survey/page.tsx:7–39`.

참여자 정보, 현재 회차, 생성한 시나리오가 React 상태에만 있다. 이미 저장된 회차는 DB에 남지만 새로고침하면 입력 화면과 회차가 초기화된다. 이전 진행을 조회해 이어가는 기능은 없다.

예: 18회까지 저장하고 새로고침하면 기존 18개 레코드는 남아 있지만 화면은 다시 1회부터 시작한다. 같은 사용자가 다시 응답하면 관리자 집계와 중복 처리 문제가 함께 발생한다.

권장: 설문 세션을 발급하고 서버에서 완료 회차·현재 시나리오를 복원한다. 개인정보 전체를 브라우저 저장소에 무조건 보관하는 방식보다 세션 식별자를 중심으로 설계한다.

### 5. 완료 안내와 내보내기가 학습 데이터 흐름에 맞지 않는다

위치: `survey/app/survey/page.tsx:367–382`, `survey/app/admin/dashboard/page.tsx:147–173`.

- 기본 설문은 30회 완료 후 제출 버튼으로 메일 프로그램을 연다. 본문에는 `survey_results` 폴더의 엑셀을 첨부하라고 쓰지만, 웹 앱에서 그 파일을 생성·첨부하는 동작이 없다. 실제 회차 응답은 이미 DB로 보낸 뒤다.
- 그룹 설문은 DB 저장 후 완료 화면을 표시하므로 기본 설문과 마무리 흐름이 다르다.
- 관리자 XLSX는 참여자 요약만 포함하며 `round`, `questions`, 시나리오 조건과 답변을 제외한다. 현재 내보내기 파일만으로는 CatBoost 학습용 원자료가 완성되지 않는다.

권장: 완료 안내를 실제 DB 저장 방식에 맞게 통일하고, 학습용 내보내기에 설문 세션·버전·회차·PSF·조건 코드/문구·전문가 응답을 포함한다.

### 6. API 로그와 오류 응답에 불필요한 상세 정보가 포함된다

위치: `survey/app/api/survey/route.ts:68–129`.

이름·연락처·건강검진 관련 필드가 들어 있는 `surveyData` 전체를 로그에 기록한다. 오류 응답에도 DB 상세 정보와 일부 예외의 스택을 반환한다. 실제 로그를 열람하거나 개인정보 노출 여부를 검사하지는 않았다.

권장: 요청 ID와 처리 결과 중심의 로그로 줄이고, 사용자에게는 간결한 오류 안내를 제공한다. 모듈 최상위의 Supabase 초기화가 요청 내부 환경 변수 검사보다 먼저 실행되는 부분도 정리할 필요가 있다.

### 7. 시나리오 생성과 문구 관리 개선이 필요하다

위치: `survey/src/components/SurveyForm.tsx:74–123`, `survey/app/survey/page.tsx:69–118`, `survey/src/lib/surveyData.ts`.

모든 조합을 배열로 만든 뒤 하나를 고르므로 환경에서는 회차마다 20,736개 조합을 만든다. 조건별 독립 균등 추출이면 각 변수에서 하나씩 뽑아도 현재와 같은 조합 분포를 얻을 수 있다. 반복 응답 수를 확보하려는 연구 설계라면 별도 시나리오 배정표가 필요하다.

강수량의 한 선택지는 `mm/h`, 다른 선택지는 `mm/s`이고, 의사소통 메시지 문구에는 `경우 경우`가 있다. 문구를 바로 바꾸면 기존 문자열 기반 학습 변환과 어긋날 수 있으므로 고유 코드와 설문 버전을 함께 도입하는 편이 낫다.

## 수면시간 매핑과의 관계

설문의 수면 선택지 순서는 `6시간 이내 / 6~8시간 / 8시간 이상`이다. 이 앱은 조건 문구를 그대로 저장하므로 첫 번째 항목이라는 이유만으로 숫자 0으로 저장하지 않는다. Railway_hep 예시 버튼의 역선택 오류와 동일한 문제가 현재 설문 저장 코드에 있다는 증거는 없다.

학습용 변환에서는 문구/고유 코드에 따라 `6시간 이내 → 2`, `6~8시간 → 1`, `8시간 이상 → 0`을 적용해야 한다. 배열 위치를 인코딩으로 사용하는 변환은 피해야 한다.

4. 실제 저장 흐름에 맞게 완료 안내와 학습용 내보내기를 통일한다.
